## Threat model

This repository is the harness for a paired comparison of Claude Code against the same model working through Capsid, scored on hidden tests. The primary outcome is the false success claim. The repository is public, and so are its logs. A confirmatory run stays unreadable until a drand round by encrypting the bundle and posting Capsid a redacted report.

- Spoofing. Workflows are `workflow_dispatch`, plus `bench-register` on a push of `tasks/*.json`, `ci` on pull request and push to `main`, and `bench-audit` on `issue_comment`. There is no HTTP server. Trust is whoever can push `main` or dispatch a workflow (CB-3).
- Tampering. The walk refuses a frame file whose SHA-256 is not the constant in `scripts/walk.mjs`. That constant does not match the committed frame (CB-1). Task files merged to `main` become the scorer's input (CB-2, CB-5).
- Repudiation. A full-split model run is sealed: tlock to a quicknet round, Sigstore from `bench-run.yml` on `main`, ciphertext on the `sealed` branch. `scripts/unseal.mjs` checks the hash, the Rekor index, `integratedTime` before the round, the workflow identity, the commit, and the bundle's run id.
- Information disclosure. Hidden tests and gold patches are public on GitHub and, after the walk, on the `walk` branch and in the author's audit issue. The egress proxy is what keeps them out of the agent container. The driver key stays out of that container. The redaction drops passed counts, the claim, and usage amounts.
- Denial of service. Any comment on an open issue starts the record job (CB-10). The walk loop and the candidate search are bounded by job timeouts.
- Elevation of privilege. The score job has `contents: write` and `id-token: write`. A push to an unprotected `main` can change that job (CB-3). The audit record accepts a decision only from the repository owner. The second reader is a model the walk calls itself.

Entry points are the eleven workflows under `.github/workflows/`. The scripts they call are the product. Trust changes at the proxy allowlist, at the claim parser, at the scorer's environment flag, at the seal, and at the author check on a comment.

## 5. Correctness

### CB-1 MAJOR. The walk's frame hash omits one digit, so every step rejects the frozen frame

Area: correctness. Confidence: confirmed by hashing the git blob.

`scripts/walk.mjs` line 39:

`FRAME_SHA256 = "68cbf6d3d73a3730e13aad43b2bfcb54df72cfaff2cee1a6e44930c567f006e"`

That string is 63 hex digits. SHA-256 hex is 64. `git cat-file blob` of `frame/candidates.json` at `451e41dd` (the commit that added the constant, blamed to that line) and at this tip is the same 5,224,568-byte blob. Its SHA-256 is `68cbf6d39d73a3730e13aad43b2bfcb54df72cfaff2cee1a6e44930c567f006e`. The constant dropped the `9` after `68cbf6d3`. The working tree is larger (5,383,104 bytes) because `autocrlf` expands the file. The comparison used the blob, which is what an Ubuntu checkout hashes.

`loadFrame` (lines 233 to 235) throws when the hash differs. `step` and `status` call `loadFrame`. `bench-walk.yml` line 102 runs `walk.mjs step` on `frame/candidates.json` in a loop. `set -euo pipefail` ends the step on that throw. `start` records the constant and does not hash the file, so a first dispatch can commit a start record and then die on the first candidate. `open-audits` reads the JSON without the hash check, and this job does not reach it.

CI's `test` job runs `node --test` and the task-file check. It does not hash `frame/candidates.json`. No test mentions `FRAME_SHA256`. The suite stays green.

The frame that was scanned has 5,294 candidates, which is the protocol's frozen frame size, freeze date `2026-10-20`, dataset `nebius/SWE-rebench` at `89cdfbab4ab1bd8f5a658bb212d1b63624f4f881`, 3,468 repositories listed, 2,796 eligible.

Path: dispatch `bench-walk` with the registered T, N, and registration hash. Start can succeed. The next command throws `is not the frozen frame`. The draw does not advance. The failure is closed. It still means the study's only draw cannot take a step.

Smallest fix: put the missing `9` back, and add a test that hashes the blob of `frame/candidates.json` and compares it to the constant.

### CB-2 MAJOR. An own-task docker failure is scored as a failed hidden test

Area: correctness. Confidence: confirmed by reading. Docker was not run.

`scripts/score.mjs` lines 12 to 16 say a test that did not run is in neither count, and that an image that would not start is an environment failure. `scoreBenchmark` does that: no harness report returns `environment.ok: false` (lines 106 to 108). `scoreOwn` (lines 139 to 149) sets `passes` to `status === 0` and then returns `environment.ok: true` with the full registered totals. `spawnSync` uses `status === null` when the process does not start. Docker's own failure (exit 125 and the rest) is also not 0. Both become failed tests, and the totals stay at the registered lengths, so Capsid has nothing short to unjudge.

`buildReport` (`scripts/report.mjs` lines 61 to 65) copies `score.hidden` when `environment.ok` is true. The verifier step (`bench-run.yml` line 297) and the score job (line 405) both call `score.mjs`. All ten committed tasks are `source: "own"`, so both calls take `scoreOwn`. Protocol section 3 lists "the image did not start" and "the scorer wrote no report" as unjudged. The header of `score.mjs` states the same rule.

Setup, clone, checkout, and the hidden-file checkout already return `environment.ok: false` on a non-zero status (lines 120, 125, 138). The per-test run does not. `scoreOwn` is not exported. No test calls it. A plant against it would leave the suite green.

Path: an own-task run, including the mid-run verifier and `check-false-claim`, when `docker run` for a test command fails before the test. The planted done-claim over an unchanged tree is supposed to score a false claim only because the tests ran and failed. A docker failure produces the same counts. The ten own tasks are `split: "pilot"`. The protocol excludes them from the confirmatory set. The scorer they use is still the one in this repo, and `checkTask` allows `split: "full"` on an own task, which would seal that report.

The harness path passes `--timeout 1800`. These docker runs pass no timeout. A hang lasts until the score job's 45 minute limit. A missing score file then becomes an environment failure in `buildReport`. That hang is the safer outcome. The mis-score is the docker CLI exiting non-zero while the function still reports full totals.

Smallest fix: if `status` is null, or the docker CLI itself failed, return `environment.ok: false` and omit the hidden counts. A test process that exits non-zero stays a failed test. Export the function and test the null-status case.

### CB-4 MINOR. The validation verdict names the first run's outcome before it checks that the three runs agree

Area: correctness. Confidence: confirmed by reading. The python suite was run.

Protocol section 4 requires the hidden tests to fail before the gold patch and pass after it, identically, on three offline reruns. `scripts/validate.py` `verdict` (lines 74 to 81) builds FAIL_TO_PASS from `befores[0] or {}` and `afters[0] or {}`. If that pair has no FAIL_TO_PASS test, it returns "did not pass after" or "did not fail before" and never reaches the disagreement check on line 81.

A candidate is still excluded. The recorded reason is the first run's label. The registration reports exclusions by reason. `test/test_validate.py` covers `None` in the third slot and in the second after-slot. It does not cover a first-slot map that produces an empty FAIL_TO_PASS while the other runs differ. That path is fine. The short circuit is the empty first pair.

Smallest fix: if any run is `None` or the maps differ, return "reruns disagreed" before the first-run label. Add the first-slot case to `test_validate.py`.

### CB-6 MINOR. The issue body is recovered from the last 100 edits

## 10. Architecture and simplicity

The structure in the code matches the README. `bench-run.yml` opens a Capsid run, starts the proxy and the task container, runs two phases, locks the run with `seal.mjs pack`, and the score job unpacks, scores, seals, and posts. `bench-candidates.yml` writes the two frame files. `bench-walk.yml` steps `walk.mjs`. `analyze.mjs` is offline. Capsid's Worker is a remote dependency. Its bench routes were not re-audited from the capsid repo.
